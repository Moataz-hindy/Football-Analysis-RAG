# Week 4 — Analytics & Intelligence Layer

## Discussion Analytics, Opinion Dynamics & Reporting

## 1. Overview

This week you will build the **analytics and intelligence layer** on top of the multi-agent discussion system developed in Week 3.

The goal is to transform raw discussion history into measurable insights about:

* Opinion change
* Agreement and disagreement
* Agent influence
* Sentiment

The analytics layer should then combine these measurements into a reusable engine and produce human-readable reports and visualizations.

By the end of the week, a completed discussion from Week 3 should be transformable from:

```text
Raw Discussion History
        │
        ▼
┌───────────────────────┐
│      Analytics        │
├───────────────────────┤
│ Opinion Change        │
│ Agreement             │
│ Influence             │
│ Sentiment             │
└───────────┬───────────┘
            │
            ▼
┌───────────────────────┐
│  Analytics Results    │
└───────────┬───────────┘
            │
       ┌────┴─────┐
       ▼          ▼
   Report      Visualizations
```

The outputs of this week will become the primary data source for the dashboard developed in **Week 5**.

---

# 2. Why This Matters

A discussion transcript by itself is difficult to analyze.

Consider a discussion containing hundreds of messages:

```text
Agent A: ...
Agent B: ...
Agent C: ...
Agent A: ...
...
```

A human may be able to read it and form an impression, but the platform needs to answer measurable questions such as:

* Did agents change their opinions?
* How much did they change?
* Did the group become more or less aligned?
* Which agents appear to have influenced others?
* What was the emotional/tonal character of the discussion?
* How did these properties evolve across rounds?

This week converts the discussion into measurable signals.

The resulting analytics should be useful both to humans and to the frontend developed in Week 5.

---

# 3. The Problem

Build a reusable analytics engine that consumes the discussion history produced by Week 3 and computes:

1. Per-agent opinion change across rounds.
2. Per-round agreement/disagreement.
3. Per-agent influence scores.
4. Per-message sentiment scores.
5. A unified analytics result containing all of the above.
6. An automatically generated human-readable report.
7. At least one opinion-trajectory visualization.
8. An interaction graph visualization.

The exact mathematical implementation, libraries, data structures, and architecture are up to you unless explicitly required below.

# 6. Opinion Change

## Objective

Measure how each agent's opinion changes throughout the discussion.

Week 3 records an opinion snapshot for each agent at each round.

Your job is to transform these snapshots into a quantitative representation of opinion trajectory.

---

## Required output

Produce a per-agent, per-round stance series.

Conceptually:

```text
Agent      Round      Stance
--------------------------------
Agent A      0         0.72
Agent A      1         0.68
Agent A      2         0.51
Agent A      3         0.42

Agent B      0        -0.30
Agent B      1        -0.18
Agent B      2         -0.05
Agent B      3          0.10
```

The exact stance scale is your responsibility.

The important requirement is that the result is **numeric and comparable across rounds**.

The Week 4 plan specifically requires a per-agent, per-round numeric stance series.

Possible approaches include:

* Mapping structured opinions to numeric values.
* Embedding-based representation followed by a dimensionality/reduction strategy.
* Another defensible method.

These are examples rather than requirements.

You should choose an approach that makes sense for the data produced by Week 3.


# 8. Opinion Change

In addition to storing stance values, calculate how much an agent moved between rounds.

Conceptually:

```text
Opinion Change
=
Stance(current round)
-
Stance(previous round)
```

For example:

```text
Agent A

Round 0: 0.70
Round 1: 0.60
Round 2: 0.45

Change:
Round 1 = -0.10
Round 2 = -0.15
```

You may use a different formulation if justified.

The important requirement is that the analytics layer captures both:

* The agent's position.
* The direction/magnitude of its movement.

---

## Acceptance criterion

The analytics output must contain at least one numeric stance value for every agent at every available round.

The output should make the trajectory of each agent inspectable.

---

# 9. Agreement / Disagreement

## Objective

Measure how aligned or divided the group is during each round.

This is a group-level metric derived from the individual stance values.

For every round, compare the agents' stances.

Conceptually:

```text
Round 1
Agent A = 0.70
Agent B = 0.65
Agent C = 0.72

        ↓

High agreement
```

versus:

```text
Round 2
Agent A = 0.90
Agent B = -0.80
Agent C = 0.10

        ↓

High disagreement
```

---

# 10. Agreement Score

Your implementation must produce **one agreement score per discussion round**.

The Week 4 specification calls for aggregating pairwise stance differences into a single score per round.

---

## Possible approach

One possible approach is:

```text
For each round:

    Calculate pairwise stance differences

    Aggregate the differences

    Convert the result into an agreement score
```

You are free to choose the exact formula.

For example, you might define:

```text
Agreement = 1 - normalized_average_pairwise_difference
```

But this is only an example.

You may use another formulation if you can justify it.

---

# 11. Agreement Score Requirements

Your documentation must explain:

* How pairwise differences are calculated.
* How they are aggregated.
* What the final score means.
* The score's range.
* What high agreement means.
* What low agreement means.

---

## Acceptance criterion

For every discussion round:

```text
Round → Agreement Score
```

must exist in the analytics output.

---

# 12. Influence

## Objective

Estimate how much each agent's arguments appear to move the opinions of other agents.

This is different from simply measuring how much an agent changed its own opinion.

For example:

```text
Agent A speaks
      │
      ▼
Agent B changes stance
      │
      ▼
Agent C changes stance
```

The analytics layer should attempt to identify whether changes in other agents' opinions are associated with another agent's contributions.

The Week 4 plan specifically calls for a **correlation-based influence metric** using per-agent, per-round stance changes and message content.

---

# 13. Influence Inputs

Your influence calculation should make use of the information available from Week 3, particularly:

* Per-agent stance changes.
* Round information.
* Message content.
* Agent relationships/interactions.

These provide the basis for estimating whether an agent's contributions are associated with changes in other agents' opinions.

---

# 14. Influence Metric

The exact implementation is your responsibility, but the metric must be **correlation-based**.

You should investigate an appropriate correlation-based formulation and clearly document your implementation.

The provided Week 4 learning resources include:

* LLM Opinion Dynamics Simulation.
* DeGroot Model and Network Imbalance.

The DeGroot material is specifically included because it provides a mathematical model for opinion influence over a network.

You are not required to blindly implement a particular model.

You should understand the approach you choose and explain how it maps onto your data.

---

# 15. Influence Output

The minimum required output is:

```text
Agent → Influence Score
```

For example:

```text
Agent A    0.72
Agent B    0.31
Agent C    0.58
Agent D    0.14
```

The numbers above are examples only.

---

## Interpretation

Your documentation should explain:

* What a high influence score means.
* What a low influence score means.
* What a negative score means, if applicable.
* What happens when there is insufficient data.
* Whether the metric measures causation or association.

Be careful not to describe correlation as proof that one agent **caused** another agent's opinion change.

# 16. Handling Insufficient Influence Data

Some discussions may not contain enough information to calculate a meaningful influence score.

For example:

* Too few rounds.
* Too few interactions.
* No measurable opinion changes.
* No relevant message/recipient relationships.

Your implementation should handle these cases explicitly.

Do not silently generate misleading values.

Possible approaches include:

```text
null
NaN
"insufficient_data"
```

or another clearly documented representation.

# 37. Interpretation vs Measurement

Be careful to distinguish between:

```text
Measurement
```

and:

```text
Interpretation
```

For example:

```text
Influence Score = 0.72
```

is a measurement.

Saying:

```text
Agent A convinced Agent B
```

is a much stronger causal claim.

Unless your methodology supports such a conclusion, prefer language such as:

```text
Agent A showed a high estimated influence score.
```

or:

```text
Agent B's opinion changes were strongly associated with interactions involving Agent A.
```

Document the limitations of your metrics.
